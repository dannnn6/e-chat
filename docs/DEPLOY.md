# Развёртывание E-chat

Инструкция относится к **пилоту 0.1.0**. Сначала локальный тест, затем отдельный тестовый поддомен и только после приёмки — ограниченная эксплуатация. Ничего из этой инструкции не требует импортировать дамп VKH или заменять его PHP-файлы.

## 1. Что нужно подготовить

Linux-сервер, отдельный DNS-поддомен, Docker Engine с Compose plugin, Python 3, доступ к репозиториям Python и контейнерных образов. Команды предполагают bash и Linux; установка Docker зависит от ОС и здесь не выполняется скрытым `curl | sh`.

```sh
docker version
docker compose version
python3 --version
```

Для небольшого пилота можно **начать планирование** с 2 vCPU, 2–4 ГБ RAM и SSD. Это ориентир для выделения ресурсов, а не измеренный минимум/вместимость. База и резервные копии требуют дополнительного диска. Если сервер уже занят VKH и другими сервисами, не отдавайте E-chat всю доступную память или все соединения PostgreSQL.

Пусть новое имя — `echat.example.com`. Это пример: замените его своим. Создайте DNS A на адрес сервера. Не создавайте AAAA без рабочего IPv6. Проверьте, какой процесс уже занимает 80/443; существующий reverse proxy лучше сохранить.

## 2. Распаковать и создать секреты

Распакуйте ZIP, например в `/opt/E-chat`. Не размещайте исходники, `.env` или резервные копии в публичном каталоге Nginx.

```sh
cd /opt/E-chat
python3 scripts/init.py echat.example.com
chmod 600 .env
```

Генератор создаёт отдельные пароль PostgreSQL-администратора, пароль ограниченного пользователя API, AES-ключ данных и код приглашения. `.env` создаётся через exclusive create; повторный запуск не перетрёт ключ.

**Не запускайте генератор заново ради «исправления подключения». Потеря `ECHAT_DATA_KEY` означает потерю возможности расшифровать серверные тексты.** Сохраните защищённую резервную копию `.env` вне сервера.

`ECHAT_REGISTRATION_TOKEN` — общий код пилотного приглашения, а не пользовательский ключ восстановления. Выдавайте его только тестировщикам. Пустое значение закрывает новые регистрации, не отключая восстановление уже существующих аккаунтов. Смена приглашения требует перезапуска API; пароли БД и ключ данных таким способом менять нельзя.

## 3. Поднять БД и API

```sh
bash scripts/up.sh
curl --fail http://127.0.0.1:3080/health/live
curl --fail http://127.0.0.1:3080/health/ready
docker compose ps
```

Скрипт собирает API, ждёт БД, явно применяет миграцию и запускает API. PostgreSQL не публикует порт наружу. API слушает на loopback-порту 3080. При конфликте порта поменяйте `ECHAT_PORT` в `.env` и адрес в reverse proxy.

API использует **отдельную роль `echat`, не postgres superuser**. Пароль администратора есть только у контейнера БД и инструментов резервирования. Инициализация роли выполняется на новом PostgreSQL volume; простое изменение пароля в `.env` не меняет пароль существующей роли.

Диагностика:

```sh
docker compose logs --tail=100 api
docker compose logs --tail=100 db
docker compose run --rm --no-deps api python -m echat check
```

Не присылайте полный `.env` или дамп. В логах проверяйте ошибки миграции, недоступность БД и файлового хранилища. Статус `healthy` не заменяет функциональные испытания.

## 4. HTTPS рядом с 1Panel / OpenResty / Nginx Proxy Manager

### Прокси работает непосредственно на хосте

Создайте **новый** HTTPS virtual host `echat.example.com` с проксированием на `http://127.0.0.1:3080`. Образец location находится в `deploy/nginx-location.conf`. Нужны Host/X-Forwarded-Proto, тайм-аут ответа не меньше 100 секунд и отключённая буферизация длинного ожидания.

Максимальный HTTP body — 320 КиБ: целый файл загружается несколькими блоками, поэтому не нужно разрешать гигабайтные POST-запросы. Не накладывайте на E-chat агрессивный глобальный лимит «1 запрос в несколько секунд»: авторизация, очередь и синхронизация используют разные запросы.

Не добавляйте этот location внутрь рабочего virtual host VKH и не меняйте его `.htaccess`. Получите сертификат для нового имени существующим механизмом вашего прокси. После изменения Nginx сначала выполните его проверку конфигурации, затем reload существующим способом управления сервисом/контейнером.

### Сам reverse proxy находится в контейнере

`127.0.0.1` внутри NPM/OpenResty-контейнера — сам контейнер, а не Linux-хост. Не указывайте такой upstream вслепую. Самый изолированный вариант — подключить **только API**, не БД, к существующей Docker-сети прокси.

Узнайте точное имя сети:

```sh
docker network ls
```

В корне E-chat создайте `compose.override.yml` (если он уже есть — объедините настройки, не перезаписывайте его):

```yaml
services:
  api:
    networks:
      private: {}
      proxy_net:
        aliases: [echat-api]
networks:
  proxy_net:
    external: true
    name: REPLACE_WITH_EXISTING_PROXY_NETWORK
```

Подставьте существующую сеть, в которой работает ваш reverse proxy, затем:

```sh
docker compose up -d api
```

Upstream в прокси: **`http://echat-api:8080`**. Внутренний 8080 и опубликованный на хост 3080 — разные порты. Не подключайте PostgreSQL к публичной сети прокси и не публикуйте 5432 в Интернет.

### Доверие заголовкам прокси

Параметр `ECHAT_TRUSTED_PROXIES` должен содержать только IP/CIDR реально доверенного прокси/его закрытой Docker-сети. Его адрес можно узнать через `docker inspect` и `docker network inspect`. По умолчанию доверяется только loopback; при Docker-проксировании приложение может видеть один адрес прокси вместо клиентских адресов, и IP-лимит будет общим для всех клиентов.

**Не ставьте `*` при доступном извне API.** IP/Origin и ограничитель не являются полноценной защитой от DDoS; публичному запуску нужен отдельный лимит/антиабьюз на шлюзе.

### Если 80/443 свободны

Можно использовать включённый Caddy:

```sh
docker compose --profile standalone up -d caddy
docker compose logs --tail=100 caddy
```

Это отдельный сценарий: **не запускайте его одновременно с уже занявшим 80/443 NPM/OpenResty**. DNS должен указывать на сервер, а получение сертификата — быть доступным. Никаких VPN/DPI-обходов эта конфигурация сама не добавляет.

## 5. Проверка первого запуска

Откройте `https://echat.example.com/health/ready`, затем главную страницу. Создайте два аккаунта в двух профилях, сохраните разные ключи и обменяйтесь ID. Проверьте текст, вложение, ответ, редактирование, удаление, группу и канал. Потом выключите сеть, отправьте текст, убедитесь в наличии очереди, закройте и откройте приложение, включите сеть.

Восстановите первый аккаунт по его ключу в третьем профиле. ID и история должны совпасть. В списке устройств отзовите старое устройство и убедитесь, что оно больше не получает API-данные.

Не используйте реальные секретные/производственные переписки до прохождения `docs/VERIFICATION.md`. Первоначальная загрузка оболочки, регистрация и новая TLS-сессия дороже, чем последующее короткое сообщение.

## 6. Резервная копия

```sh
cd /opt/E-chat
bash scripts/backup.sh
```

Скрипт кратковременно останавливает **только API этого E-chat**, делает PostgreSQL dump, архив файлов, копию `.env` и SHA-256, затем запускает API обратно. Директория `backups/TIMESTAMP` содержит секреты и тексты в восстанавливаемой форме: шифруйте её перед переносом и ограничивайте доступ. Не складывайте её на тот же диск как единственную копию.

В нескольких узлах **сначала остановите все API-писатели**. Один `pg_dump` вместе с одновременно изменяемой независимой копией файлов не гарантирует согласованную точку восстановления. Скрипт сам не управляет чужими серверами.

Проверяйте восстановление на отдельном пустом развёртывании. Проверка контрольных сумм подтверждает целостность файлов, но не работоспособность восстановленной системы.

## 7. Восстановление

Для нового сервера распакуйте ту же версию кода, скопируйте `config.env` из бэкапа в `.env` с правами 600 и выполните `scripts/up.sh` для создания **нового изолированного** развёртывания. Не генерируйте другой ключ. Затем:

```sh
bash scripts/restore.sh backups/TIMESTAMP --yes-replace-echat
```

Команда **заменяет только БД и файловый volume данного проекта E-chat**. Она проверяет SHA и совпадение имени проекта, паролей и ключа, останавливает API и восстанавливает обе части. Если восстановление прервалось, API намеренно остаётся остановленным — не запускайте его до устранения рассогласования.

Не выполняйте `docker compose down -v` на рабочем E-chat: это удаляет persistent volumes. Для обычной остановки достаточно `docker compose stop`. Для обновления кода сохраните `.env`, данные и бэкап, выполните миграцию новой версии и повторные тесты; версии схемы нельзя менять произвольно.

## 8. Несколько API-процессов на первом сервере

Первый Compose запускает 2 процесса Uvicorn. Это не 2 разных продукта и не 2 независимые БД. Для эксперимента можно изменить `ECHAT_WORKERS`, затем пересоздать API, наблюдая RAM, число соединений БД и p95 задержки. Больше процессов не всегда быстрее; предел 256 одновременных соединений установлен на процесс, а часть из них занята long-poll.

Начинайте с этого, а не с физического кластера. Приведённая конфигурация не измерялась на вашем сервере.

## 9. Второй физический сервер

Это расширение API, **не федерация и не независимая копия аккаунтов**. Необходимо:

- закрытая IP-связь между узлами, например уже настроенная WireGuard-сеть;
- одна PostgreSQL первого узла;
- одно согласованное файловое хранилище, смонтированное на обоих узлах;
- одинаковые `ECHAT_DATA_KEY`, публичная origin и настройки приглашения;
- балансировщик одного HTTPS-имени.

Ниже пример адресов `10.66.0.1` и `10.66.0.2`; замените их своей закрытой сетью. Настройка VPN и NFS не автоматизирована и не считается протестированной частью пакета.

### 9.1 Общие файлы

Сделайте бэкап, остановите API и перенесите его текущий volume в, например, `/srv/echat-shared-media`:

```sh
bash scripts/backup.sh
docker compose stop api
sudo install -d -m 0700 -o 10001 -g 10001 /srv/echat-shared-media
docker compose run --rm --no-deps -T --entrypoint tar api -cf - -C /app/data . > /tmp/echat-media-copy.tar
sudo tar -xpf /tmp/echat-media-copy.tar -C /srv/echat-shared-media
sudo chown -R 10001:10001 /srv/echat-shared-media
```

Продолжайте только при успешном завершении каждой команды. Архив временной копии тоже содержит личные файлы — после проверки переноса удалите его. Исходный volume сохраните до контрольного восстановления.

Экспортируйте эту папку **только** второму узлу через защищённую сеть. Для Linux NFS нужны сервер `nfs-kernel-server` и клиент `nfs-common`. Пример строки `/etc/exports` на первом сервере:

```text
/srv/echat-shared-media 10.66.0.2(rw,sync,no_subtree_check,root_squash)
```

После настройки экспорта и firewall смонтируйте его на втором сервере:

```sh
sudo mkdir -p /srv/echat-shared-media
sudo mount -t nfs4 -o hard 10.66.0.1:/srv/echat-shared-media /srv/echat-shared-media
mountpoint /srv/echat-shared-media
```

API работает с UID/GID 10001; права должны согласованно работать на обоих узлах. **Не запускайте второй API, если NFS не смонтирован:** Docker может иначе создать пустую локальную папку, и получится две разные истории файлов. Перед размонтированием останавливайте API. NFS-порты открывайте только в VPN, не всему Интернету.

### 9.2 Первый узел: private PostgreSQL и новый bind mount

Добавьте в `.env`:

```text
ECHAT_PRIVATE_IP=10.66.0.1
ECHAT_SHARED_MEDIA=/srv/echat-shared-media
```

Объедините с существующим `compose.override.yml` такие поля (существующие настройки сети прокси сохраняются):

```yaml
services:
  db:
    ports: ['${ECHAT_PRIVATE_IP}:5432:5432']
  api:
    volumes: ['${ECHAT_SHARED_MEDIA}:/app/data']
```

`deploy/primary-private.compose.yml` и `deploy/primary-shared-media.compose.yml` содержат соответствующие фрагменты. После проверки конфигурации:

```sh
docker compose config --quiet
docker compose up -d --wait db api
```

Откройте 5432 на VPN-интерфейсе только для второго узла. После изменения проверяйте фактические bind-адреса: **0.0.0.0:5432 здесь не нужен**.

### 9.3 Второй узел

Распакуйте тот же E-chat. **Не запускайте `scripts/init.py` и не поднимайте новую БД**. Скопируйте `deploy/node.env.example` в `deploy/node.env`, установите права 600 и заполните значения из первого узла. `ECHAT_DATABASE_URL` использует пароль роли `echat`, а не пароль postgres-администратора. `ECHAT_DATA_KEY` должен совпадать байт-в-байт.

```sh
mountpoint -q /srv/echat-shared-media || exit 1
docker compose --env-file deploy/node.env -f deploy/node.compose.yml config --quiet
docker compose --env-file deploy/node.env -f deploy/node.compose.yml up -d --build
curl --fail http://10.66.0.2:3080/health/ready
```

У этого примера нет автоматического безопасного старта после перезагрузки: сначала восстановите сетевое монтирование, затем запустите узел. Для постоянной эксплуатации нужен service manager с зависимостью от mount unit, проверкой доступности общего хранилища и мониторингом. Не объявляйте такой пилот HA-кластером.

### 9.4 Балансировщик

Образец — `deploy/nginx-cluster.example.conf`. Upstream содержит первый loopback API и второй private API. Все клиенты по-прежнему используют **одно HTTPS-имя**. Сессии находятся в общей БД, поэтому sticky sessions не обязательны; приватные ключи браузерного устройства ни на один новый сервер не копируются.

Проверьте отправку через первый узел и чтение/скачивание через второй, обрыв одного API, повтор после потери ответа и последовательность курсора. Во время восстановления бэкапа остановите оба API. Первый сервер с БД и NFS остаётся единой точкой отказа — добавление API этого не устраняет.

## 10. Эксплуатационные ограничения

Нет автоматического удаления старых событий, архивирования, S3-адаптера, репликации БД, межсерверной федерации, доставки без IP-связи и круглосуточного мониторинга. Процессный rate limiter не заменяет кластерный антиспам. Пароли и образы зависимостей зафиксированы в конфигурации только как версия пилота; перед публичным запуском нужны аудит зависимостей, секретов, резервирования и нагрузки.
