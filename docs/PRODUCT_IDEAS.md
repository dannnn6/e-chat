# Позиционирование E-chat и идеи развития

Это предложения дизайна продукта, **не утверждение, что ни один конкурент в РФ или мире не имеет подобных функций**. Рыночная уникальность отдельно не проверялась. Название E-chat и возможность использования товарного знака тоже требуют отдельной проверки.

## Что уже отражено в коде

**Прозрачная очередь, а не бесконечное «соединение».** Сообщение сначала сохраняется локально; пользователь видит очередь или ошибку. Есть явный повтор. Файлы не включаются в автоматическую фоновую загрузку.

**Текст важнее тяжёлого медиа.** В E-режиме маленькие блоки файла; новые текстовые сообщения могут быть отправлены между блоками раньше окончания тяжёлого вложения. Это помогает при коротких окнах доступной связи, но при постоянном потоке текста файл может ждать дольше.

**Контакт без публикации номера.** Пользователи обмениваются публичным криптографическим ID, а восстановление выполняется ключом. Правовой статус такой регистрации для публичного российского сервиса ещё требуется определить.

**Свой небольшой сервер.** Один пакет для собственного/семейного/командного тестового развёртывания и независимый каталог данных. Это не федерация и не обещание освобождения от обязанностей оператора.

## Предложения, НЕ реализованные в 0.1.0

### 1. «Паспорт доставки»

Отдельные проверяемые этапы: сохранено на моём устройстве → принято сервером → получено устройством адресата → реально прочитано. По нажатию — история попыток и причина задержки без раскрытия приватных системных данных. Сейчас есть очередь, подтверждение сервера и чтение личного диалога; отдельного надёжного per-device delivery ACK нет.

### 2. Режим «окно связи»

Пользователь заранее набирает сообщения и выбирает приоритетный объём — например, только тексты и подтверждения, максимум заданного бюджета за сеанс. При кратком восстановлении сети клиент сначала пересылает минимальный пакет. Для полевых работников/дороги это понятнее, чем ручное выключение всех автозагрузок. Нужны измерения на реальной 2G, ограничение фона и тесты батареи.

### 3. Два уровня вложения

Сначала миниатюра/низкобитрейтное аудио или короткое текстовое описание, оригинал — отдельно и по согласию получателя. Для документов можно отправлять название, размер и контрольную сумму прежде всего. Требуются безопасная обработка медиа и раздельная очередь оригиналов. Сейчас метаданные файла есть, адаптивного транскодирования и голосовых сообщений нет.

### 4. Контактная карточка, которая не устаревает при смене телефона

QR с публичным ID и проверяемой подписью профиля; новое устройство подтверждает ту же идентичность. Важное отличие — визуальное предупреждение о новом ключе/подмене, а не только одинаковое имя. Сейчас ID стабилен при восстановлении, но QR-обмен и независимая проверка подписи контакта не реализованы.

### 5. Частный контур с последующей синхронизацией

Для предприятия — работа в доступной локальной сети при недоступности внешнего Интернета, затем согласованная синхронизация. Это **отдельный сложный режим** с разрешением конфликтов и моделью доверия, не «поставить второй API». Офлайн-передача по Bluetooth/Wi-Fi Direct/QR тоже не входит в текущий пакет.

### 6. Лимит расходов и понятная телеметрия

Недельный бюджет трафика, расходы по чатам и типам сообщений, предупреждение до скачивания, экспорт обезличенного диагностического отчёта. Сейчас показывается только приблизительный счётчик полезного HTTP-payload текущей вкладки: это не тарифицируемый трафик оператора и не счётчик TLS/DNS.

### 7. E2EE без самодельной криптографии

Следующий безопасный этап — выбор проверенного протокола для личных чатов, независимый аудит, многопользовательская модель ключей и понятное восстановление истории. Нельзя просто объявить шифрование БД «сквозным» или хранить один общий секрет всех клиентов на сервере. Перед внедрением нужно решить trade-off: поиск на сервере, новые устройства, группы, резервирование и forward secrecy.

## Практический порядок развития

Сначала подтвердить корректность и сохранность сообщений на настоящих телефонах/БД, затем закрыть фоновые уведомления и нативный клиент, провести аудит безопасности и правовой модели. Только после этого измерять конкурентное преимущество по трафику, задержкам, батарее и поведению при обрывах. Тема для позиционирования — «не теряет действие в плохой сети и честно показывает доставку», а не технически невыполнимое «работает при любом Интернете».
