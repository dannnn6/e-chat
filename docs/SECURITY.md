# Модель безопасности и границы доверия

## Что защищает ключ восстановления

Браузер создаёт ключ ECDSA P-256 и получает публичный ID, вычисляемый из публичного ключа. Код `ECHAT1.…` содержит приватный материал восстановления и контрольную сумму. Это не 12/24 слова BIP-39, не криптовалютный кошелёк и не обещание совместимости с каким-либо блокчейном.

При регистрации и восстановлении приватный ключ **не передаётся серверу**. Сервер отдаёт одноразовый запрос; клиент проверяет origin, параметры, идентификаторы и срок действия, затем подписывает. Сервер хранит публичный корневой ключ, публичные ключи устройств и хэши сессионных токенов. Срок запроса ограничен; повторное завершение того же запроса отклоняется.

Для повседневной работы используется отдельный неэкспортируемый ключ устройства в IndexedDB/WebCrypto. Корневой ключ не сохраняется приложением как рабочий ключ после регистрации. Пользователь должен сохранить его отдельно. Это свойство WebCrypto, **не гарантия аппаратного хранения в TPM/TEE браузера**.

Уникальный ID публичен. Ключ восстановления секретен. Общий серверный код приглашения — третья отдельная сущность. `ECHAT_DATA_KEY` — четвёртый, серверный AES-ключ данных; пользовательские ключи его не заменяют.

## Чего это не защищает

**Сквозное шифрование переписки не реализовано.** Тексты шифруются AES-256-GCM перед хранением в БД, но сервер обладает ключом и расшифровывает их для участников и поиска. Администратор сервера технически может получить содержимое. Шифрование транспорта обеспечивается HTTPS и правильно настроенным сертификатом, а не одним алгоритмом входа.

Файлы хранятся в закрытой директории без публичных URL и выдаются после проверки членства, но сами файлы в серверном хранилище **не зашифрованы на уровне приложения**. Локальные сообщения и файлы PWA в IndexedDB также не зашифрованы отдельным пользовательским паролем. Используйте шифрование диска и защиту профиля ОС; это не заменяет будущий E2EE-протокол.

Отсутствие номера телефона не означает полной анонимности. Сервер/прокси видят сетевое соединение и метаданные, участники — ваш ID и сообщения. Обладатель recovery key может войти и отозвать ваши устройства. В пилоте нет ротации корневого recovery key с сохранением прежнего ID: кража корневого ключа требует прекращения использования скомпрометированной идентичности.

Сервер раздаёт сам веб-код. Компрометация сервера или внедрение вредоносного JavaScript может украсть вводимый ключ либо подписывать от имени работающего устройства. Неэкспортируемость ключа не блокирует его использование вредоносным кодом в том же origin. CSP, отсутствие CDN и `textContent` для текста уменьшают поверхность атаки, но не дают независимый аудит.

## Восстановление и выход

Сохраняйте ключ восстановления в менеджере паролей либо зашифрованном файле с независимой резервной копией. Не отправляйте его поддержке, в общий чат или публичный репозиторий. Потеряв все устройства и recovery key, пользователь не получает автоматического сброса по SMS/почте: таких каналов в продукте нет.

При восстановлении на новом устройстве по умолчанию можно сохранить другие устройства либо явно отозвать их. Через «Мои устройства» доступ отзывается на сервере. **Кнопка локального выхода удаляет рабочую авторизацию только из текущего браузера**, оставляя его локальную историю/очередь. Для серверного отзыва используйте список устройств. Очистка сайта удаляет локальные данные; не делайте этого при неотправленной очереди.

Резервная копия сервера должна включать PostgreSQL, файлы и `.env`. Наличие ключа пользователя без БД не воссоздаёт потерянную историю. После восстановления старого бэкапа возможны изменения состояния сессий/отзывов относительно более нового сервера: это нужно учитывать в процедуре восстановления, временно закрывать доступ и проверять устройства.

## Разграничение доступа

В каждом чтении/изменении диалога проверяется членство. Прямой диалог имеет одну каноническую пару. Обычный участник канала не может публиковать. Проверяются автор сообщения, роль администратора, принадлежность reply и вложений тому же диалогу, готовность загрузки и отсутствие публикации чужого файла.

Удаление участника прекращает последующий API-доступ, но не может стереть уже скачанную им информацию. Новые участники группы/канала получают доступ к хранимой истории диалога: скрытой «истории только после вступления» в v1 нет.

Авторизованное скачивание использует `application/octet-stream`, `Content-Disposition: attachment`, `nosniff`, приватные пути и проверку SHA. Встроенного антивируса, песочницы файлов и безопасного предпросмотра офисных/исполняемых вложений нет.

## Публичная эксплуатация

До внешнего запуска необходимы независимые проверки управления сессиями, XSS/CSRF, восстановления, IDOR, гонок PostgreSQL, квот, отказа диска, резервных копий, зависимостей и закрытого хранилища. Требуются политика блокировки злоупотреблений, механизм жалоб/модерации и согласованные юридические документы. Общий код приглашения, локальный rate limiter и лимит файлов — только ограничения небольшого пилота, не промышленная антиспам-система.

В этом пакете нет публичного административного кабинета, аппаратной аттестации клиента, Signal/MLS, Double Ratchet, криптографической forward secrecy истории, прозрачности ключей или проверки отпечатков безопасности собеседников. Эти слова нельзя использовать в описании текущего продукта как уже реализованные функции.

## РФ: регистрация без телефона

Проверено по доступным правовым источникам 25.09.2026. Статья 10.1 Федерального закона № 149-ФЗ предусматривает специальные обязанности организатора сервиса обмена мгновенными сообщениями, в том числе идентификацию по абонентскому номеру; также регулируются сведения идентификации и иные обязанности. В части 5 есть исключение для некоторых личных, семейных и домашних нужд, но **рабочий чат или публичный продукт нельзя автоматически объявить таким исключением**.

Поэтому схема «публичный ID + криптографический ключ» — реализованный технический способ входа, а не готовое заключение о допустимости публичного запуска без номера в России. До публикации продукта российской аудитории квалифицированный юрист должен определить статус оператора, применимые требования и допустимую модель идентификации. Возможное отделение непубличной юридической идентификации от публичного ID — направление обсуждения, а не уже решённая юридическая схема.

Источники: официальный текст 149-ФЗ на сайте Президента России `https://kremlin.ru/acts/bank/24157/page/3`; актуальная статья 10.1 в ГАРАНТ `https://base.garant.ru/12148555/baf8d0298b9a3923e3794eecbe3d1996/`. Для технического API использованы стандартные примитивы WebCrypto и библиотеки cryptography; наличие стандартных примитивов не заменяет аудит собственного протокола.
