# E-chat: архитектура и ограничения пилота

## Разделение продуктов

E-chat не является новым режимом старого `messages.php`. Это отдельный Python/FastAPI-сервис, отдельная PostgreSQL, отдельные аккаунты и браузерный клиент. VKH остаётся PHP/MySQL + Kotlin/Compose и получает отдельный DM-модуль. Обмен между пользователями двух продуктов, единый вход и федерация **не реализованы**.

Такое разделение не требует рискованно добавлять `chat_id` во все запросы общего рабочего чата, его прочтения, закрепления, поиск и загрузку файлов. Риск изменения рабочих данных VKH не переносится на публичный эксперимент E-chat.

## Клиент

`web/app.js` — JavaScript без внешнего UI-фреймворка и без CDN. `web/app.css` — адаптивная компоновка. Service Worker кэширует только оболочку приложения, но не авторизованные HTTP-ответы. IndexedDB хранит ключ устройства, сессию, локальные диалоги, ограниченный кэш сообщений, черновики и исходящую очередь по аккаунтам.

При отправке формируется постоянный UUID. Запись в IndexedDB завершается **раньше**, чем очищается поле ввода. Сеть работает отдельно. Изменения сообщений применяются по версии; курсор синхронизации и сами изменения сохраняются в одной транзакции. Запоздалый ответ истории не заменяет существующие метаданные диалога, полученные синхронизацией.

Клиент запрашивает историю страницами; в отображаемом окне не более 1000 сообщений. При чтении дальше окно сдвигается, а не бесконечно растёт. Это ограничение размера окна, **не измеренная гарантия 60/120 FPS**: DOM-отрисовка ещё не заменена полноценной виртуализацией и не профилирована на старых телефонах. Загруженная история в кэше — не офлайн-копия всей переписки.

Web Locks, когда поддерживаются браузером, оставляют одного отправителя очереди на аккаунт среди вкладок. Без этой возможности идемпотентность сервера всё равно защищает от дубликатов, но параллельные попытки могут расходовать лишний трафик.

## Сервер и таблицы

`echat/db.py` содержит явную схему версии 1. Миграция запускается отдельной CLI-командой, не из обработчика каждого HTTP-запроса. Работающий сервер проверяет версию схемы на старте. Это начальная миграция нового продукта; изменение схемы существующего развёртывания в следующих релизах потребует отдельной миграции, а не только `create_all`.

Главные сущности: `users`, `devices`, `sessions`, `challenges`, `conversations`, `members`, `messages`, `user_clocks`, `events`, `blocks`, `invites`, `uploads`.

Внутри диалога последовательность `seq` выделяется при блокировке строки диалога и сохраняется вместе с сообщением. Уникальность `(sender_id, client_id)` обеспечивает идемпотентность повторов; `(conversation_id, seq)` — однозначный порядок. Это **одна запись в БД при повторной доставке запроса**, а не обещание «exactly once» для всех внешних эффектов и сетевых систем.

У каждого пользователя отдельный `revision`. Сервер блокирует счётчики затронутых пользователей в одном порядке и записывает события в ту же транзакцию, что сообщение. Клиент никогда не должен перескочить через незавершённую транзакцию только потому, что глобальный автоинкремент выдал следующий номер. Подписчик получает только события своих диалогов, а права проверяются повторно при чтении сообщения/файла.

Для больших каналов запись события каждому участнику даёт O(N) работы на публикацию. Поэтому установлен пилотный предел 256 участников. Это **не архитектура миллионного канала Telegram**. Следующий уровень масштабирования потребует общего журнала диалога и более ленивой доставки персональных событий/счётчиков.

## Протокол

| URL / действие | Назначение |
|---|---|
| `POST /api/auth/challenge` | Одноразовый запрос на регистрацию, восстановление или вход устройства |
| `POST /api/auth/complete` | Проверка подписи и выдача сессии |
| `GET /api/auth/devices`, `POST /api/auth/revoke` | Устройства и отзыв |
| `POST /api/rpc?action=sync` | Список/изменения после пользовательского курсора |
| `create`, `history`, `send`, `edit`, `delete`, `read`, `search` | Основная переписка |
| `members`, `member`, `invite`, `join`, `block`, `mute` | Состав диалогов и настройки |
| `POST /api/uploads` | Идемпотентное создание загрузки |
| `GET /api/uploads/{id}` | Подтверждённое смещение |
| `PUT /api/uploads/{id}?offset=N` | Один блок файла |
| `GET /api/files/{id}` | Проверка членства и выдача опубликованного вложения |
| `/health/live`, `/health/ready` | Процесс и доступность схемы БД |

Ожидание `sync` до 25 секунд асинхронное: нет выделенного PHP-FPM-процесса на каждого клиента. Сообщения об изменениях PostgreSQL `LISTEN/NOTIFY` используются **как сигнал**, а не как единственное хранилище событий. При пропущенном сигнале курсор перечитывается; резервная проверка выполняется примерно раз в 5 секунд. Запросы к БД и файловые операции вынесены из event loop в потоки.

Формат передачи — JSON с HTTP gzip, а не собственный бинарный протокол. Это проще проверять и развёртывать, но не абсолютный минимум байтов. Смена на CBOR/Protobuf оправдана только после измерения, какая часть трафика приходится на JSON, TLS, заголовки и повторы.

## Докачка

На сервере `committed_offset`/`offset` — граница подтверждённых байтов. Клиент узнаёт её после разрыва и продолжает с неё. Если процесс успел записать файл, но не успел подтвердить SQL-транзакцию, следующая попытка отрезает неподтверждённый хвост перед записью. Файл считается готовым только после проверки размера и SHA-256.

Лимит блока — 256 КиБ; E-режим веб-клиента использует 32 КиБ. Перед следующим блоком проверяется готовый к отправке текст. Огромная загрузка не должна монополизировать единственную очередь приложения.

Сервер поддерживает Range при скачивании. **Веб-интерфейс пилота скачивает файл целиком через Blob** и проверяет SHA-256; продолжение прерванного скачивания в PWA ещё не реализовано. В нативном модуле VKH предусмотрены `.part` + Range + SHA-256.

## Пределы

До 200 диалогов на аккаунт, 256 участников группы/канала, 4096 символов сообщения, 4 файла по 10 МиБ, 100 МиБ суммарно зарезервированных серверных файлов пользователя, 200 исходящих сообщений / 100 МиБ в локальной очереди. История API ограничена страницами до 100 сообщений; поиск расшифровывает не более 500 кандидатов и возвращает до 50 результатов за шаг.

Пределы сервера задаются в `Settings`, некоторые соответствующие ограничения клиента зафиксированы в UI. Меняя их, обновите обе стороны и повторите нагрузочные/ресурсные тесты. Квота учитывает незавершённые загрузки и ещё не очищенные удалённые файлы. Автоматической политики retention/GC и общего ограничения количества регистраций по приглашению в v1 нет.

## Масштабирование

Горизонтально добавляются API-процессы. Им нужны одна PostgreSQL, один серверный ключ шифрования, одна публичная origin и согласованное общее файловое хранилище. Независимые локальные папки на двух серверах **не эквивалентны** общему хранилищу и приводят к пропаже файлов при балансировке.

PostgreSQL и файловое хранилище пока остаются едиными точками отказа. Добавление API не создаёт автоматическую репликацию, failover БД, федерацию, sharding или mesh-доставку. Ограничитель запросов в приложении локален процессу; общий антиспам/лимит кластера нужно вводить на шлюзе либо через общее хранилище.

Источники технических решений: Android offline-first (`https://developer.android.com/topic/architecture/data-layer/offline-first`); PostgreSQL 17 NOTIFY (`https://www.postgresql.org/docs/17/sql-notify.html`); WebCrypto (`https://www.w3.org/TR/WebCryptoAPI/`). Описанная конкретная реализация определяется файлами этого пакета, а не наличием этих механизмов в чужих продуктах.
